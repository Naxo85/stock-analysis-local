## Decisiones y garantías

### H03 — respuesta durable y compatibilidad congelada

Cada recibo nuevo de adaptive_codex conserva response_sha256 y events_sha256 (src/local_runner/adaptive_codex.py:236). authenticate_response (receipt_integrity.py:13) comprueba salida exitosa, respuesta no vacía, digest cuando existe, evidencia de eventos y coherencia de contrato con call.json cuando existe. La caché exige el digest de su recibo de origen; una entrada antigua sin él es un miss, no una firma retroactiva.

Para recibos antiguos sin digest se exige el evento original completo: un único turno y respuesta final coincidente conforme a codex_call_evidence. No se reescriben recibos congelados. Este cruce local de eventos es evidencia adicional independiente de la copia response, no una firma criptográfica emitida por el proveedor ni protección frente a un atacante que reescriba todos los originales y sellos locales a la vez. Los hashes del input, instrucciones, schema, modelo y esfuerzo siguen siendo propiedad del runner; el modelo no los declara.

### H04 — sellar lo validado y publicar la misma instantánea

publication_bundle.py:13 sella JSON/Markdown/HTML, evidencia original, input, policy, instrucciones y núcleo de review; verify_bundle:45 comprueba conjunto y hashes antes de publicar. Los artefactos se leen una vez en memoria y se publica esa instantánea; la ruta legacy recibe una copia privada verificada en validated_publication, nunca vuelve a leer el staging mutable.

La revisión adversarial encontró una ventana entre verificar staging y releerlo después de I/O remoto. Se eliminó: _publish_locked (adaptive_stage.py:789) congela artefactos, contexto y policy antes de consultar autoridad; _publish_manifest utiliza esas cadenas. Una mutación del staging durante las lecturas remotas no altera JSON, MD, HTML ni CURRENT publicados. No se pretende proteger un proceso host comprometido capaz de modificar la memoria o todas las copias privadas.

Un review.ok sin sello no autoriza firmar los espejos existentes: analyze (adaptive_stage.py:437) reconstruye y valida exclusivamente recibos exitosos originales, conserva reviewed_at original y usa receipt_itv. El test CAT copia un candidato original, corrompe su rango derivado, prohíbe calls/reserva de presupuesto y comprueba que la reconstrucción recupera el rango original. Un review.ok sellado tampoco evita comprobar frescura. Reanudar un candidato no publicado envejecido se rechaza; un recibo ya publicado puede devolver el resultado idempotente sin una nueva decisión financiera.

Cada versión confirmada tiene descriptor histórico manifest.json. Se escribe después del CAS; si falla esa escritura, el puntero actual permite leer esa misma versión y el reintento o siguiente escritor conserva su descriptor antes de reemplazar el puntero. El siguiente escritor no puede borrar esa evidencia por avanzar directamente. Una reversión exacta A→B→A se rechaza antes de cambiar el puntero: una versión histórica no adquiere un committed_at nuevo ni choca después de confirmar. La consulta histórica valida versión, símbolo, descriptor confirmado y cuerpo; ausencia, mismatch o traversal no redirigen silenciosamente a latest. El score y enlace de una fila siguen correspondiendo a la versión usada por esa sincronización aunque haya otro commit. El intento más reciente es un estado operativo actual separado y puede aparecer junto a finanzas históricas. La proyección Sheet es asíncrona; el pinning permite verificar esa diferencia temporal.
