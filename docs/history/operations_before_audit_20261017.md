# Operations Map

This repo is the local control center for the stock analysis system. Prefer
repeatable scripts and documented commands over ad-hoc terminal commands.

**Estado operativo:** antes de diagnosticar, lanzar, detener o reanudar un
lote, leer [`handoff_current.md`](../handoff_current.md). Ese archivo contiene
el estado y las incidencias mas recientes; este mapa no sustituye su relevo.

conserva o actualiza cambios rutinarios; Sol high trata cambios criticos e ITV
maximo cinco sesiones. Seis modelos simultaneos; sin fallback automatico.

[`codex_adaptive_analysis.md`](../codex_adaptive_analysis.md).

## Support/Resistance Services

Active sources:

```text
gcp_functions/support_resistances_raw/
gcp_functions/support_resistances_slim/
```

The raw service reads `TRADIER_TOKEN=tradier-token:latest` and
`GH_TOKEN=github-sr-mirror-token:latest` from Secret Manager. Never restore the
credentials embedded in an old Cloud Run source archive. Deploy raw before
slim, preserve their existing memory/timeouts/max-instance settings, and use a
new explicit revision suffix. If raw traffic is pinned to an older tagged
revision, route 100% explicitly to the newly created revision after deploy.

Verify both layers with the same ticker. The raw and slim responses must contain
`volume_profile.status=available`; every support and put wall must contain
`evidence.volume_profile` and `evidence.historical_reaction` in slim. Missing
history is represented as `status=unavailable`, never as zero evidence.

Historical support reactions use only complete five-session forward windows.
`pending_test_count` and `last_pending_observed_sessions` describe immature tests;
they do not enter success/failure counts or rebound statistics. The observation
policy is `complete_forward_window_only` in both raw and slim. This is a measurement
horizon, not a trading confirmation rule. Old frozen evidence without this policy
must not be treated as a directly comparable matured sample. Deployment check:
`.venv\Scripts\python.exe scripts\verify_support_reaction_maturity.py` (CCJ technical
data only; the service performs its normal technical JSON mirror refresh).

## Model Routing and References (compatibilidad historica)

Lo que sigue documenta el enrutado Sol/Tierra/Luna anterior y artefactos
que aun pueden contener sus nombres. **No usar esta seccion para lanzar
el flujo actual de Mercado.** El usuario retiro la propuesta de fallback
segun fecha Sol-equivalente y el recuento adicional por modelo.

An individual Excel/CLI ticker run is one operation and always uses Sol:

```powershell
.\.venv\Scripts\python.exe -m src.local_runner.run_one RKLB --run-full
```

Trading/Core batches use the current Europe/Madrid date and the authoritative
reference state. Excel exports ownership from Trading C and Core AF before it
enqueues the batch.

```text
Sunday:          owned/priority Sol; tracking Terra (new reference)
Monday-Thursday: priority Terra -> Sol reviewer when escalated
Monday-Thursday: tracking Luna -> Terra reviewer -> Sol if score >= 7
Friday/Saturday: skip
```

The Friday/Saturday skip applies to unattended calendar runs. A Trading or
Core batch launched manually from Excel forces `--analysis-mode daily` on
those two days, so it still uses the normal daily Luna/Terra routing. Sunday
manual batches keep automatic routing and therefore create the weekly
reference. Individual Excel runs remain Sol on every day.

Score promotion is 7.0, demotion is below 6.5, and 6.5-6.9 preserves the prior
tier. A daily proposed score differing by at least 1.0 is a material-change
reason; high-impact new catalysts and material thesis/narrative or
structural/technical changes are the other reasons. The confidence gate then
decides whether the change is retained, reviewed, or published directly.

The candidate model returns two confidence values in its
`ANALYSIS_ESCALATION` marker: reference invalidation and replacement quality.
The system uses the lower value. For Terra, below 65 it publishes a current
reference-retained follow-up with the official score and levels unchanged;
65-84 runs Sol, and 85 or more may publish directly with the official score
locked. A strong `structural_technical` invalidation uses a narrower review-only
threshold of 60. For Luna, below 65 publishes a fresh daily report that
keeps only the disputed conclusion aligned with the reference; 65 or more runs
Terra. Luna never publishes a material change directly. Urgent material risk
always requests the next reviewer. Mechanical report alerts, including
title-based `new_catalyst` metadata, never force a review by themselves.

Evidence caps prevent an unsupported percentage from bypassing review: none =
64 maximum, weak/ambiguous = 74 maximum, and strong evidence without independent
support = 84 maximum. The workflow stores the raw percentages, effective value,
cap, evidence summary, counterargument, decision, and reviewer outcome in the
local ticker JSON and batch summary for later calibration. A deterministic 10%
sample of otherwise-direct high-confidence Terra changes is reviewed by Sol as
a calibration audit; retries on the same ticker and date keep the same selection.

Every model can publish changed entries, targets, and stops, but it must state
the previous level, the concrete invalidation, and the rationale for the new
level. If any part is missing, it should retain the prior level. This rule is
independent of model and run type. Moving technical levels is not enough to use
`structural_technical`; that escalation is reserved for a technical change that
transforms the wider scenario or thesis.

Daily candidates are stored locally as `output/<TICKER>/candidate.*`. Retained
candidates are additionally copied below `output/<TICKER>/retained_candidates/`.
Until the review completes they cannot replace the canonical report. A retained
follow-up is uploaded as current `latest`, but embeds the unchanged authoritative
reference and carries `analysis_workflow.sheet_warning=reference_retained`; the
Sheet highlights the Note cell in pale yellow and records both dates. A non-escalated
 daily report may update its analysis and plan, but its published score is
 replaced deterministically with the official reference score.

When a newly published score differs from the previous report by at least 0.5
points, the Sheet highlights the Note cell in pale green for an increase or
pale red for a decrease. Its cell note records the previous score, new score,
delta, and visual threshold. The pale-yellow retained-reference warning takes
priority over these score-change colors. Change
`TARGET_UPDATE_SCORE_CHANGE_THRESHOLD` in
`apps_script/update_targets_and_notes.gs` to tune the threshold.

The analyst pre-step prefetches Finnhub earnings calendars with bounded
parallelism before the sequential IBKR analyst updates. Every live request keeps
its timeout and retry policy. Only after those attempts fail may the last valid
earnings calendar be used, explicitly tagged `source_status=cached_fallback`
with its age. This fallback never applies to news, catalysts, or analyst actions.

Inspect the current decision without any model or upload:

```powershell
.\.venv\Scripts\python.exe -m src.local_runner.run_batch --from-gcs --routing-plan
```

The separate reference object is:

```text
gs://stock-analysis-reports-naxo85/_analysis_state/<TICKER>/reference.json
```

If absent, the current canonical report is used once as a Sol bootstrap. A
missing/stale reference (more than seven days) forces a new reference on the
next Monday-Thursday batch. Details and remaining scheduler work are in
`docs/model_reference_automation_plan.md`.

To update analyst state and then patch/upload the corresponding `latest.json`
files in one run:

```powershell

```

Other scopes:

```powershell
cmd /c scripts\update_analyst_ratings.cmd --core
cmd /c scripts\update_analyst_ratings.cmd --tickers MU,RKLB
```

This requires TWS/Gateway listening on:

```text

```

and uses IBKR news providers:

```text

DJ-N for updates
```

Update windows:

```text
No current.json yet:
  Seed BRFUPDN over the configured seed window, then build the initial firm set.

Existing current.json:
```

```text

```

The aggregate `analyst_ratings_summary` is written to `latest.json` for Sheets
and display. It is not passed into the daily AI prompt as a general valuation
driver; the AI should only react to analyst information when there is a genuinely
recent analyst action that can act as a catalyst.

For the AI prompt, `run_one --prepare` builds a separate compact block from
`data/analyst_ratings/<TICKER>/current.json`, using the previous report
`generated_at` as the cutoff:

```text
Recent Analyst Actions Since Previous Analysis
```

Example:

```text
Acciones recientes de analistas desde 2026-06-25T00:00:00+00:00:
- 2026-06-26T15:06:17+00:00 | BTIG Research | coverage_initiated | rating=Buy (buy) | target=125 | BTIG Research initiated Robinhood Markets (HOOD) coverage with Buy and target $125
```

If there are no actions after the previous analysis, the prompt explicitly says
there are no recent analyst actions. This avoids feeding old aggregate consensus
into the daily score while still letting the model react to a genuinely new
analyst event.

## Recent IBKR News Flow

Market batch runs also refresh recent general IBKR news before the AI analyses:

```text
run_batch --from-gcs
  -> update_ibkr_news_batch
  -> ibkr_news_update per ticker
  -> data/ibkr_news_recent/<TICKER>/latest.json
  -> run_one prompt block: Recent IBKR News Headlines Since Previous Analysis
```

The news window starts at the previous report `generated_at` minus a 24h
overlap. If the previous report cannot be loaded, it tries to start at the
previous Finnhub earnings date. If that is unavailable too, it falls back to the
last 90 days. This step is non-blocking: if IBKR is unavailable, the batch logs
`ibkr_news_update.status = failed_non_blocking` and the analysis continues.

Manual update for a small scope:

```powershell
cmd /c scripts\update_ibkr_news.cmd --tickers HOOD,MU
```

After fetching headlines, the local aggregator writes:

```text
data/ibkr_news_events/<TICKER>/latest.json
```

It first merges obvious analyst-action duplicates locally. Example:

```text
Goldman Sachs maintains Buy + raises PT 108->121
```

If `GEMINI_API_KEY` or `GOOGLE_API_KEY` is available, Gemini Flash is used as a
non-blocking second pass over unresolved headlines only. It receives already
aggregated local events plus unresolved headlines, not every already-resolved
raw headline. To disable that pass:

```powershell
cmd /c scripts\update_ibkr_news.cmd --tickers HOOD --no-gemini-aggregation
```

The final prompt receives aggregated IBKR events plus any still-unresolved
headlines. The final AI decides which events are real catalysts and should
ignore noise.

To add/update `analyst_ratings_summary` in existing `latest.json` files without
rerunning the full analysis, use:

```powershell
cmd /c scripts\backfill_analyst_summaries.cmd --from-gcs
```

By default this is a dry run for GCS: it downloads each current
`gs://stock-analysis-reports-naxo85/<TICKER>/latest.json`, patches the JSON
locally under `output/<TICKER>/latest.json`, and skips tickers that do not have:

```text
data/analyst_ratings/<TICKER>/current.json
```

To upload the patched `latest.json` files back to GCS:

```powershell
cmd /c scripts\backfill_analyst_summaries.cmd --from-gcs --execute-upload-real
```

Other useful scopes:

```powershell
cmd /c scripts\backfill_analyst_summaries.cmd --core
cmd /c scripts\backfill_analyst_summaries.cmd --tickers MU,RKLB
```

This does not touch `latest.md` or `latest.html`.

## Apps Script Sync

The Apps Script project is linked by:

```text
apps_script/.clasp.json
```

Project id:

```text
1sfKDncSk4aA9MewoukGQjqAoA3jr3Z0Wj8GetXEez0wSrP8V4XPS30OO
```

Important rule: do not blindly push the whole local `apps_script/` folder if the
remote may contain newer or differently named files. The safe workflow is:

```text
1. Pull remote into a temporary folder.
2. Apply the intended patch to that pulled copy.
3. Pull a second clean remote copy.
4. Compare hashes and confirm only intended files changed.
5. Push from the patched temporary copy.
```

This is especially important because Apps Script files may be pulled as `.js`
even when local files are kept as `.gs`.

Preferred command for pushing exactly one Apps Script file:

```powershell
cmd /c scripts\push_apps_script_file.cmd apps_script\update_targets_and_notes.gs --execute-push
```

Without `--execute-push`, the command is a dry run. It pulls two temporary
remote copies, replaces only the requested file in one copy, checks that the
only diff is the expected remote `.js` file, and then pushes only when
`--execute-push` is present.

Check current clasp login/status without modifying remote files:

```powershell
cmd /c scripts\apps_script_status.cmd
```
